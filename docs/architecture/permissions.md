# 三角色权限矩阵（M0 设计约束）

| 能力 | 集团负责人 | 工程师 | 加工厂设备管理员 |
|---|---|---|---|
| 查看设备台账 | 全集团 | 授权工厂 | 本厂 |
| 新增/维护设备档案 | 可（审计） | 所授权厂 | 本厂 |
| 资产跨厂调拨/重大报废 | 集团确认 | 发起申请 | 发起申请 |
| 创建/执行巡检任务 | 可 | 授权工厂 | 本厂 |
| 上报问题/报修 | 可 | 授权工厂 | 本厂 |
| 问题分诊/工单派发 | 可 | 授权工厂 | 本厂 |
| 接单和执行维修 | 被指派时 | 被指派时 | 被指派时 |
| 验收工单 | 不得验收自己执行的工单 | 同左 | 同左 |
| 查看统计 | 全集团 | 授权工厂 | 本厂 |
| 三角色授权/工厂绑定 | 可 | 无 | 无 |

## M0 已验证的纯策略范围

- `Principal` 只接受三种 `ManagementRole`，工厂授权使用不可变快照。
- 工程师可明确授权零个或多个工厂；厂管理员最多一个工厂，零授权时不能访问任何厂。
- 只有集团负责人可管理角色/工厂授权（`can_manage_access`）。
- 验收同时要求：该工单所属工厂可访问、确为待验收、存在实际维修人记录、验收人不在任何实际维修人集合中。
- `awaiting_verification`、`factory_id` 和全部维修人集合必须由后续 Application 从持久化实体派生，
  不接受客户端自报；缺少维修人证据时拒绝验收。施工协助者也应计入实际维修人集合。

这些函数没有对外暴露，也没有账号认证、会话或撤权机制。M1 在每次请求中取得有效的最新授权，
M3 实现持久化状态机并在事务内重读/版本校验；不能拿旧的 `Principal` 快照或布尔值代替安全校验。
`awaiting_verification=False` 覆盖本示例所有非待验收状态；具体状态迁移尚未实现。
无管理角色的普通员工和受限执行者不构造管理 `Principal`，其任务凭证/本人报修能力留待后续设计。

## 避免增加角色数量但确保现场可用

- 普通员工仅需**报修、查看本人报修**时，走受限自助入口（实名身份 + 所属工厂/位置确认）。
- 非正式管理人员需参加巡检/维修时，通过明确的任务指派建立**任务级能力**，不能访问全厂资产、修改角色或任意派工。
- 受限入口不是“工程师”角色，更不是匿名可访问的全部业务接口。
- M1 必须制定员工、外协的身份来源与无飞书账号应急方案；不得以共享账号代替个人身份。
- 所有操作要记录操作者、授权来源、任务及状态上下文。

## 负面验收

1. A 厂设备管理员修改 B 厂资产，拒绝。
2. 只授权 A 厂的工程师读/写 B 厂工单，拒绝。
3. 已离职或撤权人员持旧会话继续写工单，拒绝。
4. 维修执行人尝试本人验收，拒绝。
5. 未指派执行者修改他人工单，拒绝。
6. 用户以任意 `factory_id`、资产 UUID、附件 URL 绕过数据隔离，拒绝。
