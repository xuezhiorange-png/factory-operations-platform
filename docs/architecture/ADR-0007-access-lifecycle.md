# ADR-0007：三角色人员授权、会话撤销与不可变审计（M1-02B）

任务 `FACTORY_OPS_M1_02_FEISHU_IDENTITY_AND_ACCESS` 的 B 部分，分支
`codex/m1-02b-access-lifecycle` 依赖 M1-02A（PR #6）及 M1-01（PR #5）。
继续模块化单体和现有设置/PC/H5 布局，数据库仍是唯一业务授权事实来源。

## 人员与授权

正式角色仍只有集团负责人、工程师、加工厂设备管理员，NULL 为已识别但无管理角色的账号。
首次可信飞书身份在 A 中建立待授权用户；没有公开管理员注册、按姓名/手机号匹配、部门赋权或通讯录导入。
人员列表只含本地账号、显示名、绑定状态、工厂、角色、启用状态及并发版本，不输出外部身份原始标识/令牌。

仅当前有效会话的集团负责人可访问人员列表、变更记录和写接口。写入先校验精确 Origin、
会话绑定 CSRF，再在事务中重读操作者及目标的当前资格。客户端 user_id、角色或 AI 参数不是操作者身份。
前端角色判断只控制显示，不能替代服务端权限。工厂目录继续复用原工厂服务。

工程师可显式授权零到多个启用工厂；厂管理员至多一个工厂，零范围保持待授权。
集团负责人范围是全部启用工厂，不另保存虚假“全部厂”列表。无角色账号不保留管理授权输入。
最后一位启用的集团负责人不能通过人员接口被停用或降权；需要先明确授权接任者。

## 事务、数据库约束及并发

人员变更持有事务级生命周期 advisory lock，与登录绑定/签发及离线初始化共用锁顺序；
不在锁内请求飞书。随后校验 expected_version，任何并发或重复提交使用旧版本都返回 409，
不静默覆盖，不生成重复成功审计。每次变更都要求原因。

PostgreSQL 约束是第二道边界：

- 授权行变更先锁定关联 users 行，序列化同一用户的并发授权。
- users 角色与 user_factory_access 变更均触发延迟到提交时的单厂管理员约束；
  两个事务各加一厂也不能同时成功，工程师多厂后直接改成厂管理员同样被拒绝。
- 授权版本和记录版本必须为正且单调递增；角色/启用、工厂范围、身份修改/解绑触发版本提升。
- 授权版本变化同时撤销全部现存平台会话。读接口继续检查有效会话、当前账号、绑定及版本，
  重新启用、调回原厂或重新赋同一角色不会让旧会话复活。
- 变更前后角色、启用状态、工厂 UUID、绑定状态、版本及操作原因在同事务追加 audit_events.details。
  事务审计失败，权限、版本及会话撤销全部回滚，API 不声称变更成功。

数据库所有者仍能改变 DDL/触发器，正式使用前必须分离迁移账号和最小权限运行账号；
本轮没有操作正式数据库或授予生产权限。原追加审计触发器同时保护新增 JSONB 详情；
管理 API 不提供编辑/删除历史事实的路径。

## 人员生命周期

界面在已有系统设置中新增人员管理：固定三角色、明确工厂选择、启用/停用、会话撤销、
飞书解绑和变更记录。工程师支持多厂，管理员 UI 至多一厂，服务端和数据库仍独立校验。
手机端使用卡片展示同一组字段，沿用五入口与统一抽屉。只有服务端确认成功才显示确认信息；
网络错误提示刷新核对，409 明示冲突，未授权用户无法读取人员。

人工停用可用于离职/调岗，保留角色/工厂历史并撤销会话；再启用须重新登录。
主动撤销会话也提升授权版本，即使当前没有活跃会话也建立新的失效边界。
解绑仅停用本地飞书绑定，不物理删除身份；随后该身份再次认证也不会自动重绑或创建重复用户。
解绑纠错需要受控离线核实，不接受前端任意 open_id 重绑。

真实人员事件/定期对账未接入、通讯录权限未取得，均 **UNVERIFIED**。
不能假定飞书离职会自动通知本平台；在事件经过核实并接通前，负责人必须人工及时停用。
没有 webhook 监听、同步成功提示、真实员工读取或通知发送。

## 首位集团负责人

`python -m factory_ops.bootstrap_access` 是独立离线入口，不由 Web 服务导入，不提供匿名 HTTP 路由。
需要操作员显式设置 FACTORY_OPS_ALLOW_OFFLINE_BOOTSTRAP=1、受控数据库凭据、可信应用/租户，
传入已验证待授权内部账号 UUID、当前版本、原因及 --confirm-first-group-lead。
只在没有启用集团负责人时允许一次初始化；目标须启用、无管理角色、且具备相符的有效飞书绑定。
与其他生命周期变更共用事务锁，两个同时初始化只允许一个成功，追加自举审计并撤销旧会话。
仅在隔离合成数据库测试；没有替用户初始化真实管理员或生成共享登录密码。

## 迁移与回滚

修订 `0003_access_lifecycle` 增加审计 JSONB 详情、正版本约束及上述触发器，延续 0002。
发现旧数据存在多厂管理员时直接失败并回滚，要求人工核实，不擅自裁剪授权。
空隔离 schema 可反复升级/降级；失败后可修正合成数据再重试，设备表不变。

有非空授权审计详情时，0003 降级明确拒绝擦除历史，事务不会部分移除约束。
有数据环境回退应用时保留 schema/审计并关闭人员写入口，优先前向修复；不要强制删审计或重建库。
可丢弃空测试库降级仍先撤销会话，再移除新增结构。旧 A 应用运行时可忽略新增列，
但不应使用旧迁移程序改写包含 0003 的数据库。

## 豆包边界

search_assets/get_asset_detail 与 Doubao provider 均未增加网络监听或写能力。
测试证明同一已验证外部身份在调厂/停用后也立即受当前 users/工厂授权约束；
未来只添加官方身份校验与协议封装，不引入第二套人员权限，也不让 AI 直接查库。
